## 1. Summary

The amortization page stores more than one loan scenario and switches the one being edited from a page-drawn list at the top. The list adds a scenario and removes one after confirmation. Export writes the whole set as one JSON file; import replaces the set when the file passes the same checks a load uses, and leaves the set alone when it does not. Each scenario has a prevailing monthly total: the principal-and-interest payment in effect for the most schedule months, the picture's monthly taxes and insurance, and a prevailing extra when one applied extra covers at least 80 percent of the term's months. The heading shows that total in whole dollars. A three-color bar beside the amount shows the shares, and a short legend names them. The picture and the schedule both show the prevailing extra. The per-month extra column stays.

This folder builds on [intent/complete-loan-picture/](../complete-loan-picture/spec.md), [intent/arm-loan/](../arm-loan/spec.md), and [intent/ui-followups/](../ui-followups/spec.md). Where this spec changes a sentence of one of those, D16 names it and this spec wins. Everything else in them stands. The page still calls `buildReport`. `amortize.js` does not change.

## 2. Goals and non-goals

**Goals**

- G1. Store more than one scenario, switch among them, add one, and remove one after confirmation, without dropping a loan that is already saved.
- G2. Export the whole set as one JSON file and import a file in place of the set, rejecting a file that does not validate.
- G3. Define the prevailing extra, the modal principal-and-interest payment, and the prevailing monthly total, and show the total in the heading and in the scenario label.
- G4. Show the prevailing extra in the picture table and in the schedule, beside principal and interest, and keep the per-month extra column.
- G5. Draw a PI / TI / PE bar beside the prevailing amount, and name the three parts in a short legend.

**Non-goals**

- A typed scenario name, a duplicate button, or drag-to-reorder. The label is computed.
- Any change to `amortize.js`, `compound_interest_monthly.js`, `origination_fees.js`, `amortize.d.ts`, the two skills, `node --test`, or `.github/workflows/`.
- A second amortization formula, a change to ARM rate math, or a change to what the summary's Monthly payment and the picture's Principal and interest row mean (both stay the initial `monthly_payment_cents`).
- Removing the per-month Extra payment column, or summing the prevailing extra on a year row.
- A storage listener that syncs tabs, a new npm dependency, or a network request. The file is downloaded and read in the browser. The only added storage key is the set twin of the legacy key.
- Bumping `apps/web/package.json` or `PAGES_POINT_VERSION`. That stays the owner's release step.
- Teaching the skill or the CLI about scenarios or the prevailing total.

**Release phasing.** Every requirement below is this release. Nothing is tagged later.

## 3. Principles

- P1. One walk. The prevailing figures come from one extra `buildReport` call whose extra map is the applied map and whose `arm` argument is the same object the page already passes. The schedule, the chart, and the summary keep the call they have today, which uses the requested extras. Neither call is a new formula.
- P2. A saved loan is kept. A version-1 object becomes the first scenario. A bad or unreadable import does not replace the set. Reading storage does not write it, including when the set key is corrupt. The published prototype only reads version 1, so the old key keeps the active scenario in that shape and the other scenarios live in a second key a version-1 save cannot overwrite. A save that cannot write both keys leaves the last complete pair in place.
- P3. Applied extra is what the walk applied (`extra_cents`), not the dollars typed in the cell and not a request Apply has not written.
- P4. The heading's dollar is the prevailing total, rounded the way the heading already rounds. The picture's existing total stays the sheet total.
- P5. The list is page-drawn. A native `<select>` cannot hold a trash icon or a + row.

## 4. Users and scenarios

The fresh loan is the Conventional visit: purchase price $600,000, 5% down, 30 years, note rate 7.375%, start month October 2026. Its picture is the default picture.

- A browser that already has one loan under `compound-amortization-v1` opens on that loan. The list has one row. Nothing was discarded.
- The owner adds a scenario. The new row is the fresh Conventional loan, and it is the one on screen. The previous loan is still in the list.
- The owner applies $100 in every month of the fresh loan. The heading moves from `$4,853` to `$4,953`. The bar grows a gold segment. Removing the only remaining scenario is not offered. A one-month lump that pays that loan off leaves the heading at `$4,853`.
- The owner exports, clears the site data, and imports the file. Both scenarios are back, and the one that was selected is selected again.
- A file that is not a saved set leaves the loans on screen untouched.
- On the 7/1 ARM at 5.875%, the heading shows `$5,954`, the summary's Monthly payment stays `$3,371.77`, and the schedule's Payment column still shows `$3,371.77` for the first 84 months and `$5,037.71` from payment 85.

## 5. Functional requirements

1. **The set.** The page holds an ordered list of scenarios and an active index. The scenario on screen is the active one. Every field a scenario has today stays on that scenario: the draft (`price` in dollars, `down`, `years`, `rate`, `start`), `extras`, `applied`, `prefill`, `openYears`, `picture`, and `arm` when it has been stored. Edits keep saving as they do now, into the active scenario. A term change still drops months past the term from that scenario's `extras` and `applied`. Switching scenarios loads the chosen one's stored fields into the form, the schedule, the picture, and the ARM disclosure. An invalid keystroke, an extra or index edit that has not been committed, and a picture or ARM field error belong to the scenario being left and are discarded; the loaded scenario is its last saved fields, which parse. The active index is stored with the set. Each list row's label and bar are computed from that row's stored scenario, not from the on-screen draft.

2. **Storage.** Two keys. The legacy key is unchanged: `compound-amortization-v1`, or `VITE_STORAGE_KEY` when that is set. Production and the prototype share `compound-amortization-v1`. A feature preview keeps its own legacy key and does not read or write the production key. The set key is derived from that legacy key. When the legacy key ends in `-v1`, the set key is the same string with that suffix replaced by `-v2` (`compound-amortization-v2`, or `compound-amortization-feat-<id>-v2`). Otherwise the set key is the legacy key with `-scenarios` appended. Preview keys end in `-v1`, so each preview's set stays on that preview's twin and does not meet production. The page's new functions are `loadStored` and `saveStored`. `loadScenario` and `saveScenario` stay the single-scenario helpers: `loadScenario` still reads a version-1 object from the legacy key, and `saveScenario`'s version-1 shape is what `saveStored` writes there for the active scenario.

   The set key holds version 2:

   ```json
   {
     "version": 2,
     "active": 0,
     "scenarios": [
       {
         "price": "600000",
         "down": "5",
         "years": "30",
         "rate": "7.375",
         "start": "2026-10",
         "extras": [],
         "applied": [],
         "prefill": { "monthly": "", "yearly": "", "month": 1, "open": false },
         "openYears": null,
         "picture": { }
       }
     ]
   }
   ```

   Each scenario object is the version-1 object without its own `version` field. `arm` is present only when that scenario has stored ARM, under the same rule as today. `applied` is written on every save. A missing or malformed `applied` on a scenario equals that scenario's `extras`. A missing `openYears` is null. A malformed picture falls back to the picture defaults and does not reject the scenario. A malformed `arm` is fixed mode with the ARM defaults and does not reject the scenario. Those three fallbacks are the ones load uses today.

   `loadStored` reads both keys and does not write. A valid set key is the set. A valid version-1 object in the legacy key, when there is no valid set, is `{ active: 0, scenarios: [that loan] }`. When both are valid, the legacy object is parsed with the same one-scenario rules. It differs from the active scenario when any of draft, extras, applied, prefill, openYears, picture, arm, or the presence of an `arm` key is not equal, with the maps compared by entries. That presence is what this spec calls `armStored`. It is not a field in the JSON. A difference replaces the active scenario and the other scenarios stay. Missing `applied` on the legacy object counts as equal to its extras, which is how that object already loads, so a legacy save that omitted `applied` does not look like an edit when the active scenario's applied map matches its extras. That difference is an edit made by the published prototype, or by a rolled-back production build, which can write only the legacy key. It is not a half-finished save from this page (D17). The published prototype only accepts `version === 1`. A version-2 value in the legacy key would load there as the fresh visit, and the prototype's next edit would replace every scenario. The legacy key therefore stays version 1 forever: `saveStored` writes the active scenario there in today's version-1 shape, and writes the whole set to the set key. A missing set key, a non-JSON set, a version other than 2, an empty or non-array `scenarios`, or any scenario whose loan, `extras`, `prefill`, or `openYears` would be rejected today, ignores the set key. If the legacy key then also fails, the result is the fresh one-scenario set, which is today's fallback for a corrupt key. If the legacy key parses, the result is that one loan. The other scenarios in the unreadable set are not recovered. `loadStored` still does not write, so those bytes stay until the user edits, and the next edit's save replaces the set key. An `active` that is missing, not an integer, or outside the array is read as 0 and the scenarios are kept. The legacy bytes stay on disk until the next save. A save writes every scenario to the set key, not only the active one.

   There is no `storage` event listener. Two tabs do not sync. The last successful `saveStored` replaces the whole set (D18).

   `saveStored` snapshots both keys, writes the set key, then writes the legacy key. If either write throws, it puts both snapshots back, removing a key whose snapshot was missing, and fails. The page shows `Could not save this loan.` After an ordinary edit the on-screen change stays, and storage is the last complete pair, so a reload does not treat a half-written key as a newer loan. After an import, a failed save also puts the previous set back on screen, so the screen matches that pair, and the page shows the save sentence rather than the validation sentence (D17).

3. **The list.** The first control in `<main>`, above the `h1`, is a row with the scenario button, an Export button, and an Import button. The scenario button's id is `scenario`. It shows the active scenario's label (requirement 8) and the color bar (requirement 9), with `aria-haspopup="dialog"` and `aria-expanded`. The visible label may truncate with an ellipsis. The button's accessible name is the full label. Activating it opens a page-drawn dialog labeled `Loan scenarios`, anchored under the button, and moves focus to the active scenario's row button. The dialog lists one row per scenario, in stored order. There is no cap. The row list scrolls (`overflow-y: auto`, `max-height: min(16rem, 70vh)`). The active row is `aria-current="true"`. Choosing a row makes it active, closes the dialog, and returns focus to `#scenario`. Escape, and a pointer down outside the dialog and the button, close it without switching. The button's click toggles it. Arrow Up and Arrow Down move focus among the scenario row buttons and stop at the ends. Tab order inside the dialog is, for each row, the row button then its trash button, then the next row, then the + button. The list dialog does not trap focus.

   The + control is the last row inside the dialog, not a scenario and not at the top. Its visible text is `+` and its accessible name is `New scenario`. Activating it appends a fresh Conventional scenario (`defaultScenario` at the current clock, empty extras, default picture, ARM off) and makes it active, then closes the dialog and focuses `#scenario`. It does not copy the scenario that was on screen. The new scenario's start month is `currentStartMonth` of that clock, so a scenario added in November starts in November. AC4's clock is 2026-10-15, so the added scenario starts in October 2026.

   Each scenario row has a trash button at the right edge. Its accessible name is `Remove scenario {n}`, where `n` is the row's 1-based position in the stored list. It is an inline SVG icon, not a text link. Its computed opacity is 0 until the row is hovered or the row contains focus, when the opacity is 1. When the pointer cannot hover (`hover: none`), the opacity is 1 without a hover. The button stays in the tab order while its opacity is 0. Activating it does not switch scenarios. It opens a second dialog, `role="dialog"`, `aria-modal="true"`, rendered outside the list dialog. Focus is trapped inside it and lands on `Cancel`. The list stays visible behind it and is inert: its rows do not take focus or activate, and a pointer down on the list does not choose a row and does not close the confirm. The dialog's accessible name is `Remove scenario {n}?`. The visible text includes that position and the row's label, so two rows with the same label are distinct. The buttons are `Remove` and `Cancel`. Escape and Cancel close only the confirm dialog, leave the set unchanged, leave the list open, and return focus to that row's trash button. A pointer down outside both dialogs and the `#scenario` button closes both without removing. Remove deletes that scenario and closes both dialogs, then focuses `#scenario`. If the deleted row was active, the row that shifts into its index becomes active, or the new last row when the deleted row was last, and that scenario is loaded from storage. The removed scenario's uncommitted edits are gone, and the start-month picker closes. If it was not active, the active scenario stays, its index moves down by one when it was after the deleted row, and the on-screen draft is untouched.

   While the confirm dialog is open, a click on `#scenario` does not toggle the list and does not close the confirm. The confirm stays until Remove, Cancel, Escape, or a pointer down outside both dialogs and the button.

   When the set has one scenario, that row has no trash button, and a remove does nothing. The set always has at least one scenario.

4. **Export and import.** Export downloads the version-2 document the next set-key save would write, every scenario and the active index, as `compound-loan-scenarios.json` (`application/json`). The bytes are `JSON.stringify` of that document. Import is a button labeled `Import` that clicks a hidden `<input type="file" accept="application/json,.json">`. After each `change`, the input's value is set back to empty so the same filename can be chosen again. `parseStoredSet(text)` is the pure check: it returns the set or a rejection and does not touch storage. A single leading U+FEFF is stripped before that check. A version-1 object that would load is valid and becomes the whole set: one scenario, active 0. A valid version-2 document replaces the set and selects its active index (or 0 when that index is not usable). On success the page shows that scenario, as a switch does: uncommitted extra and index edits are discarded, and the scenario list, the confirm dialog, and the start-month picker close. Focus returns to `#scenario`. `saveStored` runs immediately, so a reload keeps the imported set. A file that cannot be read, an empty file, a file that is empty after the BOM is stripped, and a file that fails validation do not change the set or either key. The page shows `This file is not a saved set of loan scenarios.` beside the buttons. A later successful import removes that sentence. A parsed file whose save then fails is requirement 2's save error, not this sentence. Import replaces; it does not merge.

5. **Prevailing extra.** "Applied extra" here is the walk's `extra_cents`, not the dollars stored in the `applied` map. The map is only the input to the walk: `buildReport` (through `loanReport`) is called with that map, the picture's financed principal, and the same `arm` argument the page uses for that product, including that scenario's stored index entries. Fixed mode passes `undefined` for `arm` even when ARM terms are stored. The denominator `n` is the parsed term in months (`years * 12` on this page). It is not `payoff_month`. The numerator `c` counts rows in `1 .. payoff_month` of that applied-map report whose `extra_cents` equals one positive amount. Months after payoff are not rows in that slice. They sit in `n` and not in `c`, so they count against the 80 percent. A positive amount is the prevailing extra when `c * 5 >= n * 4`. Otherwise the prevailing extra is 0. Exactly 80 percent of the term qualifies. A zero amount is not a candidate. Two different positive amounts cannot both qualify. The requested map is not read. A cell that differs from the applied map does not change this figure until Apply. An uncommitted keystroke does not either. The payoff month's row is in `c` when its `extra_cents` is that positive amount, and its `extra_cents` is whatever the walk applied there, which may be smaller than the request; that smaller amount is its own group. A one-month lump that pays the loan off has `c = 1` against the full term, so it is not the prevailing extra (F10).

6. **Principal and interest in the total.** On that same applied-map report, the principal-and-interest payment in effect is, for a fixed loan, `monthly_payment_cents` on every month through `payoff_month`. It is not `principal_cents + interest_cents`, which is smaller on a payoff month. For an ARM it is the row's `payment_cents` on those months, including the payoff row. That field is the scheduled payment, not `principal_cents + interest_cents`. Stored index entries change it, because they are part of the `arm` object passed to `buildReport`. The modal payment is the amount with the greatest count. A tie uses the amount whose earliest month is earlier. Months after `payoff_month` are not in the count; their `payment_cents` of 0 must not become the mode. The visible schedule can end on a different month while a cell is blue, because that table uses the requested extras. The mode still comes from the applied-map report.

7. **Taxes and insurance.** TI is `taxCents + insuranceCents + fhaMipCents + pmiCents` from `buildPicture` on the current valid picture. Each term is 0 when the picture computes 0, including a stored 0 percent, Conventional's $0.00 FHA MIP, and PMI at 20 percent down or more. The upfront MIP field is not a monthly amount; it stays inside the financed principal, as it does today. An invalid picture keystroke keeps the last valid picture, so it does not zero TI.

8. **The total, the heading, and the label.** The prevailing monthly total in cents is the modal payment plus TI plus the prevailing extra. The heading's dollar figure becomes that total rounded with `headingDollarsFromCents` and shown with `formatWholeDollars`, in the same place as today's complete payment. Its accessible name changes from `Complete monthly payment` to `Prevailing monthly payment`. The rest of the heading line is unchanged: thousands, down payment, note rate, the ARM structure label when the product is ARM, and the product select. On the fresh fixed visit the figure is still `$4,853`.

   The scenario label is the same whole-dollar amount, then ` - `, then the facts joined by ` | `: the purchase price in thousands and `K`, the down-payment text and `% down`, the note rate and `%`, the term as `{n} year` or `{n} years`, and `fixed` or the ARM structure from `armLabel` (`7/1` when the interval is 12 months, `7/6` when it is 6, otherwise `{years}/{months}mo`). The thousands text is `dollarsToThousandsText` of that scenario's stored price string, the same function the heading uses to show a valid price. The down text is the stored down string. The note rate text is the stored rate string. The term number is the parsed term, so a stored `"01"` reads `1 year` and does not keep the padding. Checked 2026-10-10: the heading's editable controls are `#price`, `#down`, `#rate`, and `#product`; the term is `#years`, below the heading; the structure label is computed text, not an input. The label includes the note rate because those editable fields include `#rate`. The label uses the last saved loan, so an invalid keystroke in the heading does not rewrite it. The fresh fixed label is `$4,853 - 600K | 5% down | 7.375% | 30 years | fixed`. The 5.875% 7/1 label is `$5,954 - 600K | 5% down | 5.875% | 30 years | 7/1`. Inactive rows use this same function on their own stored fields. The accessible name is this full string even when the visible text truncates.

9. **The color bar.** A bar shows three shares of the cent total. Left to right they are PI, TI, and PE. In the heading it is the next sibling after `span.complete-payment` and before the ` / month` text. It is not inside that span, so the span's accessible name stays `Prevailing monthly payment` and the bar is not nested in the number. On `#scenario` and on each list row the bar sits immediately after the amount.

   | Segment | What it is | Color | Token |

   | PE | The prevailing extra | gold `#8a6218` | `--prevailing-pe` |

They are shorter, and each segment's `flex-grow` is that segment's cent value in every bar, so the shares match. A segment whose cents are 0 is not rendered, so it takes no width and no border. The others fill the bar. Each rendered segment's `flex-basis` is 0. `loanCents` of the parsed loan must be greater than 0, which is the price-minus-down check and not the financed principal after upfront MIP, so the modal payment is positive and the PI segment is always present. The heading bar is `role="img"` and its accessible name lists all three amounts through `formatMoney`, including a $0.00 part that has no segment: `Principal and interest $3,936.85, taxes and insurance $916.25, prevailing extra $0.00`. A legend immediately after `.heading-line`, not inside it, reads `PI`, `TI`, and `PE` in that order, each in its token color. `headingText` does not collect those words. The fresh fixed bar is green and navy only. After F2 it has a gold segment as well. Checked 2026-10-10: `#d9a441` is 2.04:1 on the page background `--paper` `#f2f4f3`. ## 7. Design decisions

**D1 — The legacy key stays version 1, and the set lives in its `-v2` twin.** Checked 2026-10-10 in `loan.ts`: `STORAGE_KEY` is `import.meta.env.VITE_STORAGE_KEY ?? "compound-amortization-v1"`, and `loadScenario` returns the fresh visit unless `version === 1`. Production and the prototype both use the default, and the prototype is not republished, so it will keep that check. Writing version 2 into the shared key would make the prototype, and a rolled-back production, load the fresh visit and overwrite every scenario on the next edit. That fails "do not wipe a saved loan." The legacy key therefore stays the active scenario in today's version-1 shape, which is what those readers already understand. When the legacy key ends in `-v1`, the full set is that key with the suffix replaced by `-v2`, which a version-1 reader never opens. Any other legacy key gets `-scenarios` appended, so the rule still has a set key. A preview's `VITE_STORAGE_KEY` (`compound-amortization-feat-<pull-request-number>-v1`, or the branch sha form) ends in `-v1` and gets the same twin, so previews still do not share production storage or each other's sets. A version-1 object with no set key is scenario 0. When both keys exist and the version-1 loan differs, it replaces only the active scenario, which is an edit made by the prototype or an old build. Reading does not write. Putting the set only in a brand-new unrelated key, and ignoring the legacy key, was rejected because the loan already saved would not load.

**D2 — Export is the whole set. Import replaces, and a bad file does not.** One file is what the owner asked to move between browsers. Merging an import with the loans already on the page was rejected because a file is a saved set, not a patch. Load's failure mode is the fresh visit, which would discard the current loans if import used it as the replacement. Import therefore uses the same acceptance rules and, on failure, keeps the set and says so. A file that cannot be read, or that is empty, keeps the set the same way. A version-1 file is accepted because load accepts it, and it becomes the only scenario.

**D3 — Prevailing extra is applied `extra_cents` on at least 80 percent of the term.** `n` is the parsed term in months. `c` counts matching positive `extra_cents` on rows `1 .. payoff_month` of the applied-map report. Months after payoff are in `n` and not in `c`. The test is `c * 5 >= n * 4`, which accepts 288 of 360 and rejects 287 of 360 (F4) without a float. Using `payoff_month` as `n` was rejected because a lump that pays the loan off in month 1 would be 1 of 1 and would become the prevailing extra (F10: `extra_cents` 57000000, prevailing extra 0). A constant extra that pays the loan off only a little early still qualifies: 331 of 360 (F2) and 332 of 360 (F7). The amount is `extra_cents` from a walk of the applied map. The requested map still drives the schedule, so a blue cell is not yet this extra, and the visible row count is not `n`. Checked 2026-10-10: $100 in months 1–12 is 12 of 360 and does not qualify (F3).

**D4 — The payment in effect is the scheduled payment, and a tie uses the earlier month.** On a fixed loan every month through payoff is `monthly_payment_cents`. Adding that month's principal and interest would drop the payoff month into a different group. On an ARM the row's `payment_cents` is that scheduled payment, including on the payoff row; it is 0 only after payoff, and those rows are outside the slice. Stored index entries change the mode because they travel in the same `arm` object. Checked 2026-10-10: the 7/1 worst case is 84 months at 337177 and 276 at 503771, so the mode is 503771 (F5). A 15-year fixed period ties 180 against 180, and month 1's 337177 wins over month 181's 454645 (F6). Both payment counts use the applied-map report, so the mode is one slice through payoff. The prevailing extra's denominator is the term, not this slice (D3). While a cell is blue, the Payment column can differ from this mode; the mode describes the applied plan.

**D5 — TI is the four picture cents, and an empty keystroke is not a zero.** `buildPicture` already computes tax, home insurance, FHA MIP, and conventional PMI. Conventional monthly MIP is 0. PMI is 0 at 20 percent down. The upfront MIP percent is not a monthly charge. The picture treats an empty field as invalid and keeps the last valid draft, so the prevailing total does the same. A stored `0` is 0 cents.

**D6 — The heading shows the prevailing total in whole dollars. The sheet lines stay.** `headingDollarsFromCents` is the heading's rounding. On F1 the total is 485310 cents, which is today's `$4,853`, so the fresh visit does not move. On F5 the mode is the post-reset payment, so the ARM heading moves from `$4,288` to `$5,954`. The summary and the picture's Principal and interest stay the initial payment, which is what `intent/arm-loan/` says `monthly_payment_cents` is. The picture gains three rows so the new total is visible next to the sheet total.

**D7 — The schedule shows the prevailing extra beside principal and interest, and keeps Extra payment.** The column is the same amount on every month row because it is a property of the scenario, not a cash flow. The year cell is empty so it is not read as a sum of months. Putting it after Interest leaves Index immediately before Extra payment, which is where `intent/arm-loan/` placed the Index cell.

**D8 — The label is the total, a hyphen, and the heading's editable facts plus the parsed term.** Checked 2026-10-10 against `app.tsx`: the heading line is `{thousands}K | {down}% down | {rate}% {structure when ARM} {fixed|ARM} = ${whole dollars} / month`. The editable controls are `#price`, `#down`, `#rate`, and `#product`. The term is `#years`, below the heading. The label includes the note rate because those editable fields include it. The term text uses the parsed integer (`1 year`, `30 years`), not a padded stored string. The down text and the rate text stay the stored strings. The thousands text is `dollarsToThousandsText` of the stored price. The structure text is `armLabel`: `7/1`, `7/6`, or `7/1mo`. The word ARM is the product select and is not repeated in the label. The separator is ` - `. The facts use ` | `, matching the heading. The label is built from the saved scenario so a half-typed price does not name it. Inactive rows use their own stored fields. The accessible name is the full label when the visible text truncates.

**D9 — One more `buildReport` call, not a new formula.** The call uses the applied map, the financed principal, and the `arm` object `loanReport` already builds. Fixed mode passes no `arm`. The CLI and the library are untouched.

**D10 — The list is page-drawn, and + is the last row.** A native select cannot show a trash icon or a + control. The + sits at the bottom so it is not above the first loan and does not take the place of a scenario. The top of the dialog was the other place the request allowed; the bottom is the one that reads as "add after the list." The new scenario is `defaultScenario`, not a copy of the current loan. A copy would silently duplicate every extra. "Starts a new scenario" is the fresh Conventional visit at `currentStartMonth` of the current clock. There is no cap on how many scenarios the set holds. The row list scrolls. The accessible name of `#scenario` and of each row is the full label.

**D11 — Trash is on the right, shown on hover, and the last scenario stays.** The icon is at the row's right edge. Opacity 0 until `:hover` or `:focus-within` keeps it out of the way and still available from the keyboard. The check is computed opacity, not Playwright's `toBeVisible`, which treats opacity 0 as visible. `(hover: none)` shows it always, because a phone has no hover and could not otherwise remove a loan. Remove asks first, in a second page-drawn dialog, not `window.confirm`. That dialog sets `aria-modal="true"` and traps focus, starting on Cancel, so Enter does not remove. The list stays visible behind it and is inert. Escape closes only the confirm. A click on `#scenario` while the confirm is open does nothing to either dialog. Opening the list focuses the active row button. Arrow Up and Arrow Down move among row buttons. Tab order is row button, then trash, then the next row, then +. The list itself does not trap focus. The trash button's accessible name and the confirm's accessible name include the row's 1-based position, so two identical labels are not the same control. The confirm's visible text includes the label as well. Remove then closes both and focuses `#scenario`. The last row does not render the button, and the remove function refuses a set of one.

**D12 — The bar is green, navy, and a darker gold, and a zero share is absent.** The three hues are the ones already used for principal, balance, and the chart's remaining band. Green `#1b7a4d` (PI) and navy `#2a4365` (TI) stay, because each clears 4.5:1 on `--paper` `#f2f4f3`. Gold `#d9a441` is 2.04:1 on that paper, so PE is `#8a6218`, the same hue darkened until it is 4.95:1. The chart's `--remaining` stays `#d9a441`. The three are new tokens so a later chart change does not recolor the bar. The green segment is the whole principal-and-interest share, not the chart's principal band. The heading bar is 4.5rem by 0.5rem and is the sibling after `span.complete-payment`, not a child of it. The bars in the dropdown are 3rem by 0.5rem. They are shorter, and `flex-grow` set to the cent value keeps the same shares. A 0-cent segment is omitted, not drawn at zero width. A valid loan's modal payment is positive because `loanCents` of the parsed loan is greater than 0, so the bar is never empty. That check is not the financed principal. A legend after `.heading-line` reads `PI`, `TI`, and `PE` in the three colors, so a sighted reader is not left with color alone. The legend is outside `.heading-line`, and the bar has no text nodes, so `headingText` stays a walk of inputs, the select, and the heading's own text. Only the heading bar is named. The heading name carries the three amounts. `#scenario`'s name stays the full label.

**D13 — A bad active index is not a bad file. One bad scenario is. A corrupt set is not written back until an edit.** An out-of-range `active` would otherwise discard a set the owner can still use, so it is read as 0. A scenario that fails the loan parse means the file is not a set load would accept, so the whole file is rejected. `parseStoredSet` is that predicate for import. `loadStored` uses the same scenario checks. A corrupt set key is ignored and the legacy key is tried. When that legacy loan parses, it becomes the only scenario. The other scenarios in the corrupt set are not recovered, and `loadStored` does not write, so the corrupt bytes stay until the user edits. The next edit then saves the one-scenario set. When the legacy key also fails, storage load falls back to the fresh visit, which is today's behavior for a corrupt key, and that fallback is also not written until an edit. That is the corrupt-key rule, not a partial rescue of a broken file. Import does not use that fallback as a replacement: a bad file keeps both keys. P2's "a saved loan is kept" means a file or a legacy object that parses. It does not mean a half-parsed envelope is merged.

**D14 — The set in memory is the whole set.** The page keeps every scenario while it edits the active one. A save writes them all. Holding only the active scenario and saving it back would delete the others on the first edit after a version-2 load.

**D15 — This release is the whole feature.** The list, the + control, the trash icon, export, import, the prevailing total, the heading, the picture rows, the schedule column, and the bar all ship now. None is tagged later.

**D16 — What this supersedes.** Only these points, and only for the page. `intent/complete-loan-picture/` requirement 2, requirement 12, and D21: the heading dollar is the prevailing monthly total, and its accessible name is `Prevailing monthly payment`, not `Complete monthly payment`. `picture.spec.ts` follows that name. On the fresh fixed visit the dollars are still `$4,853`. The picture's Principal and interest row and its Total monthly payment row stay that spec's figures. `intent/arm-loan/` section 4 and AC9's heading after the rate is set to 5.875, and AC11's production check of that heading: `$4,288` becomes `$5,954` (F5). The structure label, the summary's `$3,371.77`, and the highest payment `$5,037.71` stay. The fixed heading at that rate stays `$4,288`, which is F5's initial payment 337177 plus TI 91625, not F6. F6 is the tie, and it happens to total the same cents. `intent/arm-loan/` AC9's "eight columns," and the eleven-column cell positions, become nine and twelve (requirement 11). `arm.spec.ts` assertions of `thead th` counts 8 and 11, and an Index cell at `nth(6)`, follow the new counts. `intent/complete-loan-picture/` requirement 6, `intent/arm-loan/` requirement 16, and `intent/ui-followups/` requirement 8: the legacy key and the per-scenario fields stay, including `applied` and `arm`, still version 1 on that key; the set around them is the set key from requirement 2. `intent/ui-followups/` requirement 11's "the heading" is unchanged except for the dollar and its name, as D6 says. Its AC5 cell indexes move right by one because of the new column: the fixed year row's Saved by extra cell becomes the seventh cell, and the ARM year row's becomes the tenth. `AGENTS.md` replaces, and does not leave beside the new text, the eight-column and eleven-column sentences, the sentence that the heading payment stays `monthly_payment_cents`, the sentence that the loan and the map are stored under `compound-amortization-v1` alone, and the Architecture and Cloud sentences that call the `$4,853` heading the complete monthly payment. Requirement 13 names each one.

**D17 — A save writes both keys, and a failed write is not a newer loan.** `localStorage` has no two-key transaction. `saveStored` snapshots both values, writes the set key, then the legacy key, and on any throw puts both snapshots back. The page shows `Could not save this loan.` An ordinary edit stays on screen so the keystrokes are not thrown away, and a reload shows the restored pair. An import whose save fails puts the previous set back on screen as well. Leaving the new legacy key beside the old set was rejected because the next load would treat that legacy loan as a prototype edit and replace the active scenario.

**D18 — Last write wins across tabs.** Each tab holds the whole set in memory (D14). The page does not listen for `storage` events and does not merge two tabs. The last successful `saveStored` replaces both keys.
