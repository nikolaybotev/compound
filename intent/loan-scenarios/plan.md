## Stops

None. The set, the migration, the prevailing definitions, the label, the bar colors, the + control, and the trash icon are decided in the spec. This design pull request does not implement them. The build starts when the owner says to build.

## Process

Review subagents read with fresh context: the spec against the intent, then this plan against the spec, on Sonnet as the owner named. Build subagents run on Composer 2.5 as the owner named. Three phases, three pull requests into `main`, each merged when CI is green, in this order: storage and prevailing math (0), the scenario list and the heading (1), the bar, the picture rows, and the schedule column (2). Each phase edits only `apps/web/**`, `AGENTS.md`, `REVIEW.md`, and this file. `amortize.js`, `compound_interest_monthly.js`, `origination_fees.js`, the skills, and `.github/workflows/` have no diff in any phase (AC11). `intent/complete-loan-picture/`, `intent/arm-loan/`, and `intent/ui-followups/` are not edited; where this spec changes a sentence of theirs, D16 names it and this spec wins.

Phase 0 keeps the full scenario list in memory and writes it back, even though the switcher is not on screen yet. A version-1 visit still shows that one loan. The legacy key stays version 1. The heading dollar does not change until Phase 1.

## Phase 0 — Storage envelope and prevailing math

Files: `apps/web/src/loan.ts`, `apps/web/src/app.tsx`, `apps/web/unit/loan.ts`, `apps/web/e2e/extras.spec.ts`, `AGENTS.md`

1. In `loan.ts`, add the stored-set type `{ active: number; scenarios: Scenario[] }`, `loadStored`, `saveStored`, and `parseStoredSet`. The set key replaces a trailing `-v1` with `-v2`. A legacy key that does not end in `-v1` gets `-scenarios` appended. Preview keys end in `-v1`, so they stay isolated. Parsing one scenario object stays the current field rules: loan, extras, prefill, and openYears must parse, a missing or malformed `applied` copies extras, picture and arm use their current fallbacks (requirement 2, D1, D13). `loadStored` reads both keys and does not call `setItem`. A valid set key is the set. A valid legacy version-1 object with no valid set is one scenario at index 0. When both are valid, the legacy object differs from the active scenario when any of draft, extras, applied, prefill, openYears, picture, arm, or the presence of an `arm` key is not equal. That presence is `armStored`. It is not a JSON field. Compare the maps by entries. A missing `applied` on the legacy object equals its extras, so a version-1 save that omitted `applied` is not a difference when the active scenario's applied map matches its extras. A difference replaces only the active scenario (F8). A bad set key is ignored. If the legacy key parses, the result is that one loan and `loadStored` does not write, so the corrupt set bytes stay until the user edits. If the legacy key also fails, the result is the fresh one-scenario set, also unwritten until an edit. An unusable `active` becomes 0 and the scenarios stay.
2. One serializer writes a scenario object with no `version` field. `arm` is omitted when `armStored` is false, on a set-key scenario and on the legacy wrap. `applied` is always written. `saveStored` snapshots both keys, writes version 2, `active`, and every scenario (those objects, no per-scenario `version`) to the set key, then writes the active scenario to the legacy key as that same object plus `version: 1` (`saveScenario`'s shape). If either write throws, it restores both snapshots, removing a key whose snapshot was missing, and fails. The page shows `Could not save this loan.` An ordinary edit stays on screen. An import whose save fails puts the previous set back on screen. There is no `storage` event listener (D18). `loadScenario` and `saveScenario` keep their version-1 behavior so existing unit tests that expect `stored.version === 1` and a top-level `arm` stay as they are. Do not change `unit/arm.ts`.
3. Point the page's `readInitial` and `persist` at the set. The React state holds the list and the active index. `persist` replaces the active scenario and saves the whole list (D14). Do not save from `loadStored`. Until Phase 1 there is no switcher, so the page still edits only the active scenario, but a set with several scenarios round-trips, and an edit still leaves `stored.arm` at the top level of the legacy key for the existing Playwright specs.
4. Add `prevailingExtraCents(report, termMonths)` and `modalPaymentCents(report)` in `loan.ts`. Both slice `report.schedule` to `payoff_month`. `termMonths` is `n`. The extra helper groups `extra_cents` on rows `1 .. payoff_month` and applies `c * 5 >= n * 4` to positive amounts only, where `n` is the parsed term in months and not `payoff_month` (requirement 5, D3). F10 is `c = 1`, `n = 360`, prevailing extra 0. The payment helper returns `monthly_payment_cents` when `report.arm` is absent, and otherwise the `payment_cents` mode with the earlier-month tie (requirement 6, D4). Add `prevailingTotalCents(modal, lines, extra)` as the sum of the modal payment, `taxCents + insuranceCents + fhaMipCents + pmiCents`, and the extra (requirements 7 and 8). Add `scenarioFigures(scenario)`: parse that stored scenario, call `buildPicture`, call `loanReport` on its applied map with the financed principal and the same arm argument the page uses for that product, and return the modal payment, the prevailing extra, the four TI cents, and the total. The heading, `#scenario`, and every inactive row call this one function so they cannot disagree. The page does not have to render these yet. Fixed mode passes `undefined` for `arm` (D9).
5. Unit tests in `apps/web/unit/loan.ts` for AC1 and AC2, using the F1–F10 numbers. Build the reports with `loanReport` or `buildReport` rather than hard-coding the mode. F10's prevailing extra is 0. `parseStoredSet` is called with raw strings. Assert it does not call `setItem`. Assert a set-key scenario has no `version` field and omits `arm` when ARM was not stored. Assert a storage whose second `setItem` throws leaves both keys unchanged. Assert `{` in the set key beside a valid legacy loan returns that loan and writes nothing. Assert a legacy key `compound-amortization` uses set key `compound-amortization-scenarios`. Do not change `unit/arm.ts`: its version-1 save assertions still describe the legacy key.
6. `apps/web/e2e/extras.spec.ts`, the test "AC8 reload keeps the edited cell, the prefill, and an open 2027": after Apply the page has written a valid `compound-amortization-v2`. The later `setItem("compound-amortization-v1", "{")` then reloads expecting the fresh visit. A valid set key wins over a corrupt legacy key, so that reload must also `removeItem("compound-amortization-v2")` before it expects the fresh visit. The earlier reload in that test, which keeps the edited cell, still passes because the set key holds the edit. No other e2e file corrupts the legacy key after a save.
7. `AGENTS.md`: the storage sentences gain the legacy key staying version 1, the set-key rule (`-v2` when the key ends in `-v1`, otherwise `-scenarios`), the version-1 migration, the prototype merge rule, the corrupt set that is not written until an edit, the two-key save and its rollback, and the do-not-wipe rule. Replace the sentence that the loan, the map, the prefill, the picture, and which years are open are stored under `compound-amortization-v1` alone. Leave the column-count sentences and the heading-payment sentences for later phases. Things agents get wrong: do not write version 2 into `compound-amortization-v1`; do not drop the other scenarios when saving the active one; do not leave one key new and the other old after a failed save. `REVIEW.md` waits for Phase 2 so Compliance is added once, with the Bugs lines, when the behavior those lines name is all on the page.
